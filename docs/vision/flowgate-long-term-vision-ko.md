# FlowGate 장기 비전 — 대화로 설계하고, 카드로 실행하고, 결과로 증명한다

> **문서 성격:** 제품 방향·설계 원칙 기록. 구현 지시서(R/N/D/WP/T)가 아니며, 현재 구현 완료 또는 기능 제공을 주장하지 않는다.
>
> **기록일:** 2026-11-01
>
> **상태:** 장기 비전 / 단계적 구현 구상
>
> **핵심 문장:** **대화는 요구사항을 이해하고 실행을 지시하는 곳, 디자이너는 AI가 실행 가능한 플로우를 구성하고 작업·검수·승인·실행을 끝까지 수행하는 곳.**

---

## 1. 왜 FlowGate를 만드는가

FlowGate의 목표는 사용자가 여러 AI에게 문서 작성, 작업, 검수, 반려 대응을 일일이 지시하고 결과를 다시 옮겨 붙이는 과정을 줄이는 것이다.

현재까지는 사용자가 N을 요청하고, NR을 확인하고, D·WP·T 등을 반복 요청하며, 매번 다음 단계를 수동으로 진행시켜 왔다. 사용자는 AI를 활용하면서도 AI들의 작업을 관리하는 데 너무 많은 시간을 쓰고 있다.

FlowGate가 궁극적으로 제공하려는 경험은 다르다.

> 사용자가 AI와 대화하며 원하는 것을 충분히 설명한다. 마지막에 **“다 이해했지? 알아서 카드 배치하고 실행해.”**라고 지시한다. 그러면 시스템이 필요한 카드를 구성·배치하고, 의존관계에 맞춰 실행하며, 검수·반려·재작업·승인까지 진행한다. 사용자는 디자이너를 통해 어디까지 왔는지 보고 결과를 확인한다.

사용자가 설계서를 직접 배치하고, 카드마다 AI를 할당하고, 다음 단계마다 명령하는 것이 최종 목적이 아니다. 사용자는 제품의 **목표·조건·방향·완성 결과**에 집중해야 한다.

## 2. 대화와 디자이너의 역할을 명확히 나눈다

### 2.1 대화: 요구사항 논의, 이해 정렬, 실행 의사 전달

- 대화는 사용자와 AI가 요구사항·제약·선택지·의문을 토론하는 인터페이스다.
- 사용자 지시에 따라 AI는 대화 내용을 실행 가능한 작업 구조로 해석하고, 디자이너에 카드를 **생성·배치**하도록 한다.
- 사용자는 자연어로 플로우 구성을 지시할 수 있으며, 대화 AI가 내부적으로 카드 구성과 실행 진입을 연결한다.
- **대화 채널이 직접 소스 수정·테스트·셸 명령·배포를 수행하는 우회 경로가 되어서는 안 된다.**
- 현재 대화가 직접 처리할 수 있는 작업/실행 기능은 장기적으로 **축소 또는 차단**하고, 해당 행동을 목적별 카드에 위임한다.
- “알아서 배치하고 실행해”라는 자연어 명령은 **채팅에서 직접 개발 작업을 수행하라는 뜻이 아니다.** 디자이너에서 플로우를 만들고 정식 실행 엔진으로 시작하라는 사용자 의사다.

### 2.2 디자이너: 실제 작업 생명주기와 가시성

- AI가 필요한 카드를 자동으로 배치하며 사용자가 매번 직접 캔버스에 카드를 그릴 필요가 없게 한다.
- 실행 순서와 의존관계를 시각적으로 표시하고 분기와 합류도 표현한다.
- 작업, 검수, 반려, 재작업, 승인, 완료, 실패를 실제 상태에 맞게 추적한다.
- 사용자가 전체 진행 상황을 한눈에 보고, 필요한 시점에 결과 확인·개입을 할 수 있다.
- 내부적으로는 문서·작업계획·의존관계·승인 근거가 유지될 수 있다. **사용자가 WP를 수동 작성하지 않아도 되는 것**과 **시스템에 계획이 없어지는 것**은 다르다.

### 2.3 모든 실행은 적합한 카드의 책임

| 하고 싶은 일 | 사용해야 할 기능 |
| --- | --- |
| 요구사항 논의·의도 정리 | 대화 |
| 작업 구성·카드 배치·진행 관찰 | 디자이너/플로우 |
| 소스 작성·수정 등 개발 작업 | 작업 카드 |
| 테스트와 테스트 결과 확인 | 테스트 카드 |
| 명령어·빌드·프로세스·서버 실행 | **실행 카드**(향후 신설) |
| 검수·승인 및 게이트 판정 | 해당 검수/확인 카드와 승인 흐름 |

대화, 작업 카드, 테스트 카드, 실행 카드가 같은 일을 여러 경로에서 중복 수행하지 않게 한다. 특히 AI 채팅의 임의 직접 실행으로 문서 이력과 검수 게이트를 우회하지 않는다.

## 3. 핵심 운영 모델 — 한 번 시작해서 끝까지

목표하는 주요 경험:

1. 사용자가 요구사항을 확정하고 전체 실행을 시작한다.
2. 실행 엔진은 준비된 그래프에 따라 카드를 순서대로, 또는 의존관계가 허용하면 **병렬로** 실행한다.
3. 지시/작업/설계 결과물은 정해진 검수 게이트에서 확인한다.
4. 반려되면 같은 작업 문맥에서 수정·재검수한다. 승인 가능한 상태까지 이어지는 자동 흐름을 지향한다.
5. 한 작업 단계가 Q&A·검수·대기 중이라고 전체 실행이 완료된 것으로 오인하지 않는다.
6. 플로우의 마지막 단계까지 실제로 도달했을 때만 종료로 판단하고, 결과와 근거를 남긴다.

### 병렬 작업의 활용

- 의존성이 없는 **설계서 여러 개를 병렬로 작성·검수**할 수 있다.
- 백엔드/프론트엔드/테스트 등 독립 분기를 병렬 진행한 뒤 필요한 합류 조건에서 통합할 수 있다.
- 작업을 빠르게 진행하는 것뿐 아니라 누가 무엇을 하고 있고 어디서 막혔는지 시각화하는 것이 중요하다.
- 병렬 실행 시 충돌하는 변경·자원 사용·승인 게이트를 존중한다. 병렬화 자체가 검수 우회가 되어서는 안 된다.

## 4. v0.2 프리셋 — 작업계획 프리셋과 다른 출발점

**새 프리셋은 기존 WP의 문서 순서 프리셋을 단순히 재현하는 기능이 아니다.** 사용자가 초기에 만들고 싶은 결과물을 고르면 디자이너 플로우와 필수 자료가 생성되는 **프로젝트 시작 템플릿**이다.

예상 사용자 동선:

1. 개발 언어를 선택한다. 예: Python, Go, TypeScript 등.
2. 초기 목표(init)를 선택한다. 예: Hello World, 간단한 게임, 간단한 웹서버.
3. 프리셋에 따라 디자이너에 **R·T·확인/승인 등 필요한 카드와 연결 관계**가 자동 구성된다.
4. 실행 가능한 상태에서 사용자는 전체 실행을 누른다.
5. 작업·검수·승인·결과 확인까지 자연스럽게 연결한다.

### AI가 없는 경우에 대한 장기 구상

- 등록/지정된 AI가 없어도 프리셋에 따라 가능한 **기본 문서와 프로젝트 구성**을 채운 상태로 시작할 수 있도록 구상한다.
- 초기에는 레포트 등 결과 문서를 제외하고 미리 준비 가능한 문서를 채우는 방식이 현실적인 단계일 수 있다.
- **TR2 흡수 이후**에는 레포트와 실제 반영 결과, 소스까지 충분히 구성된 결과를 한 번에 보여주는 방향을 검토한다.
- 이 구상은 **현재 보장 기능이 아니다.** TR2 미흡수 등 선행 조건 때문에 뒤로 미룰 수 있다.
- AI 미사용 프리셋이라 해도 실행되지 않은 작업을 실행·검증 완료로 허위 표시하지 않는다.

## 5. 실행 카드 신설 — FlowGate 내부에서 실제로 실행한다

실행 카드는 AI에게 '작업해 줘'라고 쓰는 문서 카드가 아니라 **자동화 명령과 프로세스를 수행하는 노드**다.

예상 역할:

- 명령/스크립트 실행
- 빌드 수행
- 서버/프로세스 시작·상태 확인·정지
- 실행 결과·종료 코드·로그 수집
- 다른 카드에 후속 결과 전달
- 배포 또는 실행 환경 준비와 연동

테스트는 테스트 카드로, 일반 명령은 실행 카드로 분리하는 것이 원칙이다.

이 구조가 갖춰지면 빌드/테스트 자동화를 통해 **CI**를 구성할 수 있다. 배포 파이프라인이 연결되면 **CD** 영역으로 확장할 수 있다. 단순 웹서버 시작만으로 CD가 완성된 것은 아니다.

추후에는 **터미널 버튼**도 마련해 FlowGate 내부에서 명령 실행 상태와 로그를 보고 필요한 조작을 할 수 있도록 하고 싶다. 웹서버 실행 및 미리보기까지 연결되면 FlowGate 밖으로 나가지 않고 결과를 직접 확인할 수 있다.

실행 카드의 보안·안전성 경계(실행 주체/권한, 작업 디렉터리, 환경 변수/비밀 관리, 명령 허용 범위, 시간·자원 한도, 네트워크/포트, 프로세스 정리)는 실제 설계에서 다뤄야 한다. 사용자 승인 조건과 기존 검수 이력을 생략하는 방식으로 구현하지 않는다.

## 6. 궁극적인 사용자 경험 — 보여주기용 조합 GIF가 아니라 한 번에 재현 가능한 데모

기존 v0.1 README 데모 GIF는 여러 동작을 이어 붙인 형태여서 사용자가 그대로 따라 하기가 번거롭다.

목표하는 v0.2 데모는 훨씬 단순하다.

> **언어 선택 → ‘간단한 웹서버’ 프리셋 선택 → 카드 자동 생성 → 전체 실행 한 번 → 소스·검수·승인·서버 실행 → 브라우저에서 결과 확인.**

복수의 GIF를 조합하지 않고 **실제 사용 과정을 처음부터 끝까지 한 번의 연속 데모로 보여주는 것**이 목표다.

이는 단순히 화면이 멋있어지는 문제가 아니다. FlowGate 내부 계약을 미리 배운 사람만 사용할 수 있는 도구에서, **처음 만난 사용자도 원하는 결과물을 얻는 도구**로 바뀌는 것이다.

그 수준의 경험과 안정성을 확보했을 때 GitHub의 **main에서 v0.2를 전면에 내세우는 것**을 고려한다. v0.2의 첫 자동 승인 성공만으로 즉시 main을 전환하겠다는 뜻은 아니다.

## 7. AI팀 기능에 대한 방향

- 장기적으로 FlowGate 자체가 작업 계획, 역할 배정, 병렬 실행, 검수·재작업을 통합한다면 **별도의 'AI팀' 기능이 반드시 필요하지 않을 수 있다.**
- 이는 아직 확정된 삭제 결정이 아니다. AI팀이 제공하려던 가치가 플로우와 대화의 자동 구성에 흡수될 가능성을 검토한다.
- 사용자에게 모든 AI의 역할과 배치를 직접 정하도록 강요하지 않고, 필요하면 자동 배정하되 **모델 선택·비용·권한에 대한 사용자의 명시적 제어**를 존중한다.

## 8. 개발 순서와 판단 기준

이 장기 구상은 한 번에 모두 구현할 계획이 아니라 단계적으로 완성할 목표다.

1. **기반 안정화:** 기존 v0.2의 작업 → 검수 → 반려/재작업 → 최종 승인 → 다음 단계가 정상 완주하는지 확인. 카드 생성·AI 역할 지정·실행 상태와 화면 표시도 정합성 확보.
2. **v0.2 사용성 강화:** 프리셋으로 플로우 구성과 시작 부담을 줄이고 실행/테스트 카드, 실행 결과 확인 기능을 도입.
3. **개발 환경 연결:** 터미널, 웹서버 실행, 미리보기, CI/CD 등 작업 결과를 실제로 구동하는 능력 확장.
4. **대화 중심 자동 구성:** 사용자의 요구사항 대화를 바탕으로 AI가 카드와 의존관계를 생성·배치하며, 정식 플로우 실행 경로로 작업을 시작.
5. **고도화:** 설계·개발 병렬화, 분기/합류, 자동 역할 구성, 반복적인 검수·재작업의 안정화, AI 없는 프리셋과 TR2 통합 등.

순서는 구상이며 실제 작업은 기능 성숙도와 선행 조건에 따라 조정할 수 있다.

## 9. 바뀌면 안 되는 원칙

1. **대화는 이해와 지시, 카드가 실행을 담당한다.**
2. **실행은 기록 가능하고 검수 가능한 경로를 지나야 한다.** 채팅 직접 실행이나 임의 상태 변경으로 게이트를 우회하지 않는다.
3. **사용자가 카드를 직접 배치해야만 하는 UX를 최종 목표로 삼지 않는다.**
4. **사용자가 수동으로 WP를 만들지 않아도 내부의 계획·의존관계·근거는 보존한다.**
5. **실제 실행 상태와 시각적 상태는 일치해야 한다.** 끝나지 않았는데 종료/실패를 선언하지 않는다.
6. **병렬화와 자동화는 정합성·권한·비용·안전성을 해치지 않아야 한다.**
7. **결과 중심의 진입 경험을 만든다.** 설명을 읽기 전에 프리셋 하나로 실제 결과를 확인할 수 있게 한다.
8. **최종 지향점은 'AI들에게 작업을 시키기 위해 또 다른 관리 노동을 하는 도구'가 아니라 '필요한 결과물을 AI들이 스스로 만들어 주는 도구'다.**

## 원문의 의도를 보존하기 위한 메모

- “**다 이해했지? 알아서 카드 배치하고 실행해.**” — 대화 AI는 실행의 대체 경로가 아니라 플로우 자동 구성·기동의 입구다.
- “**작업? 디자이너에 작업카드 깔고 해. 실행? 테스트면 테스트카드 이용하고 커맨드면 실행카드 있잖아.**” — 역할 중복을 없애고 카드 경계를 명확히 한다.
- “**프리셋 하나 선택해서 카드 다 만들고 실행만 누른다. 알아서 웹서버까지 실행되면 난 그냥 확인만 하면 된다.**” — 제품 경험과 GitHub 데모의 지향점이다.
- “**AI팀이란 게 필요 없을지도?**” — 통합 오케스트레이션이 별도 팀 UI를 대체할 수 있다는 가능성이지, 확정 폐지 지시가 아니다.

이 문서는 특정 버전의 현황 보고나 즉시 개발 요청이 아니라, 향후 기능·UX·아키텍처의 선택이 충돌할 때 우선 참고해야 할 **제품 비전 기록**이다.
